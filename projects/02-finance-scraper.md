> 💼 公司内部工具，源码不公开。本文档描述方案、我的职责、技术难点与成果。

## 📌 项目背景

运营需要定时**批量采集某金融平台商户中心的收款流水**，原本纯人工逐页导出，效率低、易出错。

## 🙋 我的职责

独立完成需求调研、抓包逆向、工具开发、分发打包全过程。

## 🏗️ 方案演进（v1 → v2）

```
v1: 浏览器自动化 (Playwright)            v2: 直调内部接口
┌──────────────────────┐               ┌──────────────────────┐
│ 模拟登录 → 点击导出     │   抓包发现     │ 复用登录态 → 直调       │
│ → 等待 → 下载解析       │  内部 API     │ 内部分页接口 → 解析      │
│ ⏱ ~95 秒/次            │ ───无签名───▶ │ ⏱ ~39 秒/次            │
└──────────────────────┘               └──────────────────────┘
                                        ✅ 数据 100% 对齐 v1
```

## 🔑 核心实现

- **v1**：用 Playwright 模拟人工操作导出，能稳定跑通但慢
- **关键决策**：在 v1 已经能用的情况下，我主动抓包分析，**发现平台内部 API 没有签名校验**
- **v2**：直接调用内部分页接口重写采集逻辑，跑到 ~39 秒，且与 v1 结果逐条比对 **100% 对齐**
- **分发兼容性加固**：内置 Python 运行时打包，目标机器无需安装环境即可运行；做了"扩展挂了不影响主流程"的兜底机制
- **风控意识**：采集时间随机化，避免固定整点被平台风控识别（这是从另一个被风控的老模块吸取的教训）
- **双备份策略**：v1 验收后 commit 备份，v2 验收后再备份，每次大改都有可回退点

## 🐛 难点（面试可讲）

- 平台表单字段被 UI 框架的选中态元素遮挡，照 HTML 直接写选择器会失败 → 改用语义更稳的选择器策略
- 用 `pythonw` 静默运行时 `stdout=None`，任何 print 都会导致进程崩溃 → 在入口处重定向输出到文件
- "已经能跑了，还要不要继续优化？"—— 我选择抓包重写，结果性能腰斩、数据全对齐。这种工程判断是这个项目最有价值的部分。
